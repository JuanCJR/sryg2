# Deployment (Render + Neon)

## Current state

`render.yaml` defines two services. Every merge to `main` that touches a service's `buildFilter` paths redeploys it.

- `sryg-web` (static): builds with `corepack pnpm install --frozen-lockfile && corepack pnpm --filter "@sryg/web..." build`,
  publishes `apps/web/dist` and rewrites `/*` to `/index.html` (SPA deep links such as `/personal`).
- `sryg-api` (node, free plan): builds with `corepack pnpm install --frozen-lockfile --prod=false && corepack pnpm
  --filter "@sryg/api..." build` (`--prod=false` because `NODE_ENV=production` would otherwise skip devDependencies
  such as `typescript`), starts with `node packages/db/dist/migrate.js && node apps/api/dist/main.js` and is health
  checked on `/health` (liveness, never touches the database). Migrations run in `startCommand` because
  `preDeployCommand` is only available on paid plans; there is a single instance, so no concurrent migrators.
- There is no `databases:` block: PostgreSQL is Neon, and its URLs are dashboard secrets.

Node 24 is selected with the `NODE_VERSION` env var (Render documents `NODE_VERSION`, `.node-version` and
`package.json` `engines`; `.nvmrc` is not documented, so it is not relied on). pnpm runs through `corepack pnpm`, which reads
`packageManager` from the root `package.json`. Do not use `corepack enable`: Render ships `/usr/bin/pnpm` on a read-only
filesystem, and `corepack enable` fails with `EROFS` while trying to replace it.

`VITE_API_URL` is optional while the web app is demo-driven: it builds without it, and only `fetchJson` calls fail (with
a clear message) when it is unset in production.

### Environment variables

| Service | Key | Source |
|---|---|---|
| `sryg-api` | `NODE_VERSION`, `NODE_ENV` | fixed in `render.yaml` (`24`, `production`) |
| `sryg-api` | `DATABASE_URL` | dashboard secret: Neon **pooled** URL |
| `sryg-api` | `DATABASE_MIGRATION_URL` | dashboard secret: Neon **direct** URL |
| `sryg-api` | `JWT_SECRET` | generated by Render (`generateValue`, 256-bit base64) |
| `sryg-api` | `CORS_ORIGIN` | dashboard: full origin of `sryg-web`, e.g. `https://sryg-web.onrender.com` |
| `sryg-web` | `VITE_API_URL` | dashboard: full origin of `sryg-api`, e.g. `https://sryg-api.onrender.com` |

`CORS_ORIGIN` and `VITE_API_URL` are typed by hand because Render's `fromService` only exposes a host, not a full
origin. Changing `VITE_API_URL` requires a redeploy of `sryg-web` (it is inlined at build time).

`sync: false` variables are only prompted during the **initial** Blueprint creation. When an existing Blueprint is
synced (for example, when a new service or a new `sync: false` key is added), Render ignores them, so they must be added
by hand in the service's Environment tab (https://render.com/docs/blueprint-spec, "Prompting for secret values"). Do not
replace them with placeholder `value:` entries: a sync re-applies `value:` and would overwrite the real secret. Values
added in the dashboard are preserved on later syncs even though they are not in `render.yaml`.

### Neon setup

1. Create a Neon project (Postgres 17) and a database.
2. Copy two connection strings, both with `sslmode=require`:
   - pooled (host contains `-pooler`) -> `DATABASE_URL`, used by the running API.
   - direct (unpooled) -> `DATABASE_MIGRATION_URL`, used by the migrator and the operator seed.
3. Keep both URLs in a password manager, never in the repository.

### First deploy and seeding the admin

1. Render dashboard -> Blueprints -> `sryg` -> Manual sync (or New -> Blueprint on first import). On an existing Blueprint
   the new `sryg-api` service is created without its `sync: false` variables: add `DATABASE_URL`,
   `DATABASE_MIGRATION_URL` and `CORS_ORIGIN` in `sryg-api` -> Environment, then Manual Deploy. (On a first import
   Render prompts for them instead.)
2. The first start applies all migrations to the empty Neon database (`Migrations applied.` in the logs).
3. Set `VITE_API_URL` on `sryg-web` to the `sryg-api` URL and redeploy `sryg-web`.
4. Seed the admin from the operator machine (credentials are never stored on Render), using the direct URL:
   `DATABASE_MIGRATION_URL=<direct url> SEED_ADMIN_EMAIL=... SEED_ADMIN_PASSWORD=... SEED_ADMIN_NAME=... pnpm db:seed:admin`.
   The seed is idempotent. Never run `pnpm db:seed` against production: it loads fictitious development data
   (it refuses to run with `NODE_ENV=production`).
5. Load the reference catalogs (license types, type and class ratings, aircraft, observations… transcribed from SLYM,
   see `docs/slym-catalogos/`), also from the operator machine with the direct URL:
   `DATABASE_MIGRATION_URL=<direct url> pnpm db:seed:catalogs`. It loads no people or users and is idempotent: items
   that already exist under the same name, including ones an administrator edited, are left untouched.
6. Smoke test: `curl -fsS https://sryg-api.onrender.com/health` (200), `/health/ready` (200), then
   `POST /api/auth/login` with the seeded admin returns a token.

## Limits and cold starts

- Render free web services spin down after idle; the first request takes about a minute.
- Neon free compute scales to zero; the first query after idle is slower. `/health` does not query the database so
  health checks do not keep Neon awake; use `/health/ready` to check the database.
- Free tiers have no SLA; this deployment is for validation, not production load.

## Rollback

- Render: Events/Deploys -> pick a previous successful deploy -> Rollback (static site and API).
- Migrations are additive in this change; rolling the API back does not undo them. To reset a throwaway Neon database,
  drop and recreate the branch/database and redeploy.
- A bad commit on `main`: revert it with a new commit; Render redeploys.
